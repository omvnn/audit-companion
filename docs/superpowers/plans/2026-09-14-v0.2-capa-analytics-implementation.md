# Audit Companion v0.2.0 CAPA & Analytics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a consolidated CAPA Register, deterministic CAPA summary, per-audit analytics, and cross-audit management analytics without creating a second source of truth.

**Architecture:** Keep `audits`, `audit_responses`, `findings`, and `corrective_actions` authoritative. Add a small schema migration plus RLS-safe reporting views, then consume those datasets through focused service methods. Render CAPA and analytics in new isolated frontend modules; keep calculations deterministic, traceable, and dependency-light.

**Tech Stack:** Vanilla JavaScript ES modules, Vite 6, Node built-in test runner, Supabase Auth/PostgreSQL/PostgREST/RLS/Storage, GitHub Actions, AppDeploy.

**Spec:** `docs/superpowers/specs/2026-09-14-v0.2-capa-analytics-design.md`

## Global Constraints

- Production remains `v0.1.0` until implementation, QA, security verification, and deployment verification all pass.
- Target release is `v0.2.0`.
- Raw operational tables remain the source of truth; analytics must not duplicate audit/CAPA records into a second operational store.
- Default management summaries are deterministic; no audit text is sent to an external AI service in v0.2.0.
- Reporting must preserve existing RLS boundaries.
- Admin and Lead Auditor receive global CAPA/management analytics navigation; Auditor and Viewer receive per-audit analytics only for readable audits.
- No opaque overall “audit score” in v0.2.0.
- Use lightweight CSS/SVG rendering; do not add a chart dependency unless implementation proves native rendering unmaintainable.
- Controlled-template export remains a separate v0.2.x feature.

- [ ] **Step 3: Implement minimal pure helpers**

Use these exact rules:

```js
export function safeRate(n, d) {
  return Number(d) > 0 ? Math.round((Number(n) / Number(d)) * 1000) / 10 : null;
}

export function agingBucket(days) {
  const n = Math.max(0, Number(days) || 0);
  if (n <= 30) return '0-30';
  if (n <= 60) return '31-60';
  if (n <= 90) return '61-90';
  return '>90';
}

export function isOverdue(row, today = new Date().toISOString().slice(0,10)) {
  return Boolean(row?.due_date && row.status !== 'closed' && row.due_date < today);
}
```

### Task 2: Database schema and RLS-safe reporting views

**Files:**
- Create: `supabase/migrations/008_capa_analytics.sql`

**Interfaces:**
- Produces REST-readable views:
  - `v_capa_register`
  - `v_audit_analytics`
  - `v_finding_analytics`
- Adds `findings.closed_at timestamptz`
- Adds `corrective_actions.root_cause_category text`

- [ ] **Step 1: Write migration with constrained root-cause categories and closure trigger**

Migration must:

```sql
alter table public.findings
  add column if not exists closed_at timestamptz;

alter table public.corrective_actions
  add column if not exists root_cause_category text;

alter table public.corrective_actions
  drop constraint if exists corrective_actions_root_cause_category_check;

alter table public.corrective_actions
  add constraint corrective_actions_root_cause_category_check
  check (root_cause_category is null or root_cause_category in (
    'people_competency','procedure_documentation','equipment_calibration',
    'process_method','material_sample','data_system','environment',
    'supplier_external','other'
  ));
```

Create a `public.sync_finding_closed_at()` trigger function that sets `closed_at = now()` when status changes to `closed` and clears it when status changes away from `closed`.

- [ ] **Step 2: Create `v_capa_register` with security-invoker behavior**

The view must join `findings → audits → labs → corrective_actions` and expose canonical due date as:

```sql
coalesce(ca.due_date, f.due_date) as due_date
```

Calculate `overdue`, `days_open`, `closure_days`, and `aging_bucket` from source timestamps. Use source-table RLS rather than SECURITY DEFINER bypasses.

- [ ] **Step 3: Create `v_audit_analytics`**

Aggregate readable checklist responses and findings per audit. Evidence coverage must count an answered response as covered when `evidence_text` is non-empty OR an `evidence_files.response_id` exists. Use `nullif(...,0)` for denominators.

- [ ] **Step 4: Create `v_finding_analytics`**

Expose audit/lab/month/classification/requirement reference/process stage/root-cause category/owner/status and timing fields needed by the management UI.

- [ ] **Step 5: Add targeted indexes only where missing**

Add indexes for `findings(due_date,status)`, `findings(closed_at)`, `corrective_actions(due_date)`, and `corrective_actions(root_cause_category)` if absent. Do not add materialized tables.

- [ ] **Step 6: Apply migration to the linked Supabase project**

Use Supabase migration tooling (`apply_migration`) so the change is tracked, then verify the three views are readable by an authenticated account with existing RLS semantics.

- [ ] **Step 7: Run security advisor and record findings**

Confirm no new RLS/security-definer warnings are introduced by analytics. Existing known warnings must be distinguished from newly introduced warnings.
