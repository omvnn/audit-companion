# Audit Companion v0.2.0 — CAPA Register & Analytics Design

Status: Design approved
Target version: v0.2.0
Current production version: v0.1.0
Date: 14 September 2026

## 1. Objective

Extend Audit Companion from a single-audit execution workspace into a management-capable audit intelligence system while preserving the existing audit records as the source of truth.

v0.2.0 adds four connected capabilities:

1. A consolidated CAPA Register across accessible audits.
2. A deterministic CAPA management summary, with optional AI deep analysis designed as a later permission-gated capability.
3. Per-audit statistics and analytics.
4. Cross-audit management analytics for trends, recurrence and follow-up performance.

The design follows a hybrid architecture: database views/RPCs provide secure, reusable reporting datasets; the frontend renders tables, filters and charts.

## 2. Design principles

- Raw audit data remains authoritative. Analytics must not duplicate operational records into a second source of truth.
- Metrics must be explainable. Avoid a black-box overall audit score in v0.2.0.
- Deterministic summaries are the default. No audit text is sent to an external AI service by default.
- Existing RLS remains authoritative. Reporting views must not widen data access.
- Management analytics must be useful without exposing data a user could not otherwise read.
- Every aggregate should be traceable back to the underlying audit, finding or CAPA record.
- Mobile views should prioritize summary metrics and filters; dense tables may use horizontal scrolling or progressive disclosure.

## 4. Data model changes

### 4.1 Findings closure timestamp

Add:

```sql
findings.closed_at timestamptz null
```

Rules:

- when `status` changes to `closed`, set `closed_at` if it is null;
- when a closed finding is reopened, clear `closed_at`;
- do not use `updated_at` as a proxy for closure time.

This enables reliable closure-time analytics.

### 4.2 Root-cause category

Add to `corrective_actions`:

```sql
root_cause_category text null
```

Allowed v0.2.0 values:

- people_competency
- procedure_documentation
- equipment_calibration
- process_method
- material_sample
- data_system
- environment
- supplier_external
- other

The free-text `root_cause` field remains unchanged and is still required for real analysis. The category exists only to support aggregation and trend analysis.

Future AI assistance may suggest a category, but a human must confirm it before saving.

### 4.3 CAPA due date canonical rule

The existing schema contains due-date fields on both `findings` and `corrective_actions`.

For v0.2.0:

- `corrective_actions.due_date` is the canonical CAPA due date;
- reporting views use `coalesce(corrective_actions.due_date, findings.due_date)` for backward compatibility;
- the UI should keep both values synchronized while legacy data is present;
- a future migration may remove the duplicate field only after backward compatibility is no longer required.

### 4.4 CAPA status

Do not add a second CAPA status column in v0.2.0.

Use `findings.status` as the lifecycle status:

- open
- action_pending
- verification
- closed

This avoids two independent status fields for one corrective-action lifecycle.

## 6. Metric definitions

### Per-audit

| KPI | Definition |
| --- | --- |
| Audit completion | answered checklist items / total checklist items |
| Conformity rate | conform results / answered items |
| NC rate | (minor NC + major NC) / answered items |
| Evidence coverage | answered items with evidence text or uploaded evidence / answered items |
| Findings breakdown | counts by Observation, OFI, Minor NC, Major NC |
| CAPA closure rate | closed CAPA / total CAPA |
| Overdue CAPA | due date < current date and status != closed |
| Average closure time | average(closed_at - finding/CAPA creation time) for closed items |
| Open CAPA age | current date - creation time |
| Findings by clause | count grouped by requirement reference |
| Findings by process stage | count grouped by linked checklist process stage |

If a denominator is zero, show `—` rather than a misleading 0% where appropriate.

### Management analytics

Audit activity:

- total audits
- audits by month
- audits by lab
- draft / active / review / closed distribution

Audit-result trends:

- conformity trend over time
- NC rate trend over time
- findings per audit
- findings by lab
- findings by ISO clause
- findings by process stage
- classification trend

CAPA performance:

- total CAPA
- open CAPA
- action pending
- awaiting verification
- closed CAPA
- overdue CAPA count
- overdue percentage
- closure rate
- average closure days
- aging buckets: 0–30, 31–60, 61–90, >90 days
- owner workload
- root-cause category distribution
- repeat finding indicators

## 7. Repeat-finding detection

v0.2.0 uses deterministic recurrence logic rather than semantic AI matching.

A repeat pattern is flagged when multiple findings occur across separate audits with:

- the same lab,
- the same or parent/child-related ISO requirement reference,
- and the same process stage where available.

Minimum threshold for a repeat indicator: two findings across two separate audits.

The UI must label this as a `repeat pattern` or `recurring finding signal`, not as proof that the previous CAPA was ineffective.

Optional AI semantic recurrence detection is out of scope for the default v0.2.0 release.

## 9. CAPA deterministic management summary

Generate from reporting data, not from an LLM.

Example structure:

> 27 CAPAs are visible in the selected period. 11 remain open, including 4 overdue. 3 are awaiting verification. Average closure time for completed items is 19.4 days. Equipment / Calibration is the most common root-cause category. Material Lab shows 3 recurring findings related to ISO 7.1.5.

Rules:

- every statement must be computable from the current filtered dataset;
- if data is insufficient, omit that sentence rather than infer;
- numbers in the summary should be clickable/filterable where practical;
- summaries should update when filters change.

## 10. Optional AI Deep Analysis

Not enabled by default in v0.2.0.

The UI may reserve a disabled or feature-flagged `Deep Analysis` action for a future release.

Future requirements before enabling:

- explicit organization/admin opt-in;
- approved AI provider and data-processing terms;
- configurable redaction/minimization;
- clear indication of which fields leave the application;
- human review of AI output;
- no automated status/closure decisions;
- no AI-written statement may overwrite source records without an explicit user action.

## 11. Per-audit Analytics UI

Add an `Analytics` section within each audit.

Recommended composition:

1. KPI row: completion, conformity, NC rate, evidence coverage, overdue CAPA.
2. Result distribution: horizontal bar or compact stacked bar for Conform / Observation / OFI / Minor / Major.
3. Findings by ISO clause: ranked horizontal bars.
4. Findings by process stage: ranked horizontal bars.
5. CAPA status: Open / Action Pending / Verification / Closed.
6. CAPA aging: small distribution chart.
7. Repeat-pattern callout when applicable.

Avoid decorative charts. If a chart does not help answer a management question, use a number or table instead.

## 13. Charts and rendering

v0.2.0 should prefer lightweight browser-native rendering rather than adding a large charting dependency unless implementation effort becomes disproportionate.

Recommended order:

1. CSS-based bars/progress visuals for simple distributions.
2. Lightweight SVG generated by existing JavaScript for trends and grouped bars.
3. Only introduce a chart library if multiple complex charts make custom rendering harder to test and maintain.

All charts require textual labels and should remain understandable without color perception.

## 14. Frontend structure

The current `views.mjs` is already large. v0.2.0 should avoid adding all new analytics rendering into that file.

Recommended modules:

- `analytics.mjs` — pure calculation/formatting helpers where calculations are not done in SQL.
- `analytics-view.mjs` — management and per-audit analytics rendering.
- `capa-view.mjs` — CAPA Register rendering and filters.
- `service.mjs` — data access methods only; no presentation logic.
- `app.mjs` — navigation and event orchestration.

Existing audit rendering can remain in `views.mjs` for this release, but new analytics should be isolated.

## 15. Service-layer additions

Expected service methods:

- `capaRegister(filters)`
- `managementAnalytics(filters)`
- `auditAnalytics(auditId)`
- `repeatFindings(filters)` or equivalent data included in management analytics
- `saveCAPA(...)` extended to include `root_cause_category`
- `setFindingStatus(...)` to consistently manage `closed_at`

Do not put SQL-like metric calculations into DOM code.

## 16. RLS and security

Reporting views must preserve the same access boundaries as source tables.

Preferred implementation:

- views should use invoker permissions / security-invoker behavior where supported;
- no `SECURITY DEFINER` reporting function should bypass audit-read rules;
- if RPCs are required, they must explicitly filter through existing `private.can_read_audit(...)` logic or equivalent safe source views;
- run Supabase security advisors after migrations;
- test Admin, Lead Auditor, Auditor and Viewer independently.

## 17. Error and empty-state handling

- No audits: management page explains that analytics will appear after audits exist.
- No CAPA: CAPA Register shows a clean empty state, not zero-filled fake charts.
- Partial data: metrics using unavailable dates show `—`.
- Legacy CAPA without root-cause category: show `Uncategorized`.
- Legacy due date: use the compatibility `coalesce` rule.
- Failed analytics request: operational audit entry/editing should still remain usable where possible.

## 18. Testing requirements

### Unit tests

Add coverage for:

- overdue calculation
- aging bucket boundaries
- closure-time calculation
- evidence-coverage calculation
- zero-denominator behavior

- reporting views return only readable audits;

- a Viewer cannot modify CAPA through reporting endpoints;

### UI QA

Desktop and mobile:

- CAPA table filters
- analytics date/lab filters
- chart labels and empty states
- long finding/action text
- overdue visual treatment
- print/export behavior where applicable

## 19. Export considerations

v0.2.0 analytics should support CSV export for:

- filtered CAPA Register
- management KPI/detail datasets where useful

Controlled company-template export remains a separate high-priority v0.2.x capability and should use these same source datasets rather than a duplicate reporting store.

## 20. Performance

Initial implementation may query reporting views directly because the current app scale is small.

If data volume later causes noticeable dashboard latency:

1. add targeted indexes based on real query plans;
2. aggregate through RPCs;
3. consider materialized summaries only after measurement.

Do not introduce caching/materialized analytics prematurely.

## 21. Versioning

This approved scope targets **v0.2.0**, because it introduces new user-facing subsystems rather than a patch-level fix.

The current production application remains **v0.1.0 until the implementation is completed, verified and promoted**.

At implementation completion, update together:

- `package.json` → `0.2.0`
- root `VERSION` → `0.2.0`
- changelog/release documentation → v0.2.0 entry
- project summary / README current milestone

Do not mark v0.2.0 released before QA and deployment verification pass.

## 22. Out of scope for the first v0.2.0 implementation

- autonomous AI CAPA decisions
- AI-generated audit findings without human confirmation
- semantic repeat-finding matching
- enterprise SSO
- companywide rollout governance
- materialized analytics warehouse
- arbitrary BI/report builder
- automatic controlled-template parsing

## 23. Success criteria

v0.2.0 is successful when:

1. Admin/Lead Auditor can see a consolidated CAPA Register across audits they are permitted to read.
2. The deterministic summary accurately reflects the active register filters.
3. An individual audit exposes useful result/CAPA analytics without changing its source records.
4. Management Analytics shows cross-audit trends, risk concentration and follow-up performance.
5. Recurring finding signals can be identified deterministically.
6. RLS prevents analytics from exposing inaccessible audits.
7. Metrics are tested and traceable to source records.
8. Mobile and desktop views remain usable.
9. CI, database verification and deployment QA pass.
10. Only then is the release version promoted from v0.1.0 to v0.2.0.
