# Audit Companion v0.3.0 — Audit Plan Import Design

Date: 14 September 2026  
Status: Approved design — implementation not started  
Target release: v0.3.0  
Headline: **Import the plan. Audit Companion builds the audit.**

## 1. Objective

Replace the current manual clause-by-clause audit creation flow as the primary path with an import-first workflow that reads a formal audit plan, extracts its inspection items and metadata, reconstructs a digital audit plan, and seeds the operational audit/checklist only after one final user review.

The existing manual creation flow remains available as a fallback.

## 2. Product decisions

Approved decisions:

1. **Import/Scan is the default audit-creation path.**
2. **Create manually remains available as a fallback.**
3. The importer detects clauses automatically; users do not select clauses one by one in the normal import flow.
4. The importer treats each inspection row as the primary unit. Repeated ISO clauses must not collapse distinct inspection items.
5. The original inspection-item wording is preserved unless the user explicitly edits it.
6. A document-quality gate runs before extraction. Blurry, cropped, low-resolution, glare-affected or otherwise unreadable pages are rejected rather than guessed.
7. For multi-page plans, only failed pages need to be reuploaded when the remaining pages are readable.
8. Deterministic OCR/table extraction is the default path.
9. AI fallback is allowed only when the document is readable but deterministic structural extraction is uncertain.
10. AI never creates the audit directly. Extracted output must pass schema validation and confidence rules first.
11. The system builds a full digital plan and presents one review screen before audit creation.
12. The original uploaded plan becomes a linked audit source after creation for traceability.
13. Current production remains v0.2.0 until v0.3.0 implementation, QA, security checks and deployment verification pass.

## 4. Extraction model

### 4.1 Audit-level metadata

The importer attempts to extract:

- department / lab
- audit title / activity
- audit date
- applicable standard
- objective
- scope
- criteria
- auditor names
- lead auditor if identifiable
- auditee names
- document number if present
- document revision if present
- page count

Extracted names are text until explicitly mapped to existing application users. The importer must not silently assign a person to an application account from an approximate name match.

### 4.2 Inspection-item fields

Each plan row is preserved as an independent item with:

- original row number, when present
- source page
- source row/order
- ISO clause / requirement reference
- exact inspection item / question
- Document Review flag
- Inquiry flag
- On-site Inspection flag
- other inspection method text, when present
- expected evidence, when explicitly present
- section / process heading, when identifiable
- extraction confidence values

Repeated clauses are valid. Example: five separate rows under clause 7.2 remain five checklist items.

### 5.4 Promotion into operational audit records

Only after final confirmation:

```text
audit_plan_imports       -> audits
audit_plan_import_items  -> checklist_items
original source document -> audit_sources
```

The promotion should be transaction-safe. If creation fails midway, the operation rolls back rather than leaving a partial audit.

The existing `audit_sources` table remains the permanent source-document record after promotion. The importer should store original filename, storage path, extracted text, parser identity/version and parse notes there.

## 6. Document quality gate

Quality checks occur before semantic extraction.

Reject or request reupload when any required content is affected by:

- excessive blur
- insufficient resolution
- crop cutting off required table/header content
- severe perspective distortion that prevents reliable table recovery
- glare or overexposure covering required text
- underexposure / low contrast preventing reliable OCR
- unsupported file type
- missing/corrupt page
- table structure not recoverable with sufficient confidence

### Required behavior

- Do not silently continue with unreadable required content.
- Do not invent missing words, clauses or method ticks.
- If one page fails in a multi-page upload, preserve readable pages and request only the failed page again.
- Replacing a page invalidates and regenerates extraction items originating from that page.

Example user-facing error:

> **Page 2 cannot be imported**  
> The inspection table is too blurred to read reliably. No audit has been created. Retake or reupload Page 2.

## 7. Confidence and validation rules

Initial thresholds:

- **High:** >= 90% — accepted into the review model automatically.
- **Medium:** 75–89% — eligible for AI fallback when enabled.
- **Low:** < 75% — do not guess; reject affected row/page or require reupload.

Thresholds are implementation defaults and must be testable/configurable rather than scattered magic numbers.

### Critical-field handling

Certain fields are treated more strictly than ordinary metadata:

- unreadable inspection question -> reject affected row/page
- unreadable requirement reference -> reject affected row/page when the requirement is expected by the plan
- ambiguous table row boundary -> AI fallback if enabled; otherwise reupload/manual fallback
- ambiguous inspection-method tick -> AI fallback if enabled; if unresolved, require reupload or explicit review before creation
- uncertain audit date -> show a review warning; do not guess silently
- uncertain person name -> show a review warning and allow correction

The review screen emphasizes exceptions. High-confidence values do not require row-by-row approval.

## 8. AI fallback architecture

AI fallback is secondary, not the default extraction engine.

### Trigger

Use AI only when:

1. the page passes the quality gate,
2. deterministic OCR/table extraction has usable text,
3. structure remains ambiguous, and
4. the organization-level AI fallback setting is enabled.

### Data minimization

Send only the smallest necessary unit, typically the affected page or region plus the required extraction schema. Do not send unrelated audits, CAPA history, authentication tokens, internal database identifiers or other company records.

### Authority boundary

AI output is untrusted structured input. It must pass:

- schema validation
- allowed field/value validation
- clause/method normalization checks
- confidence checks
- import ownership/RLS checks

AI cannot:

- create an audit directly
- mark audit results
- create findings/CAPA automatically
- overwrite operational records without explicit user confirmation

### Organization control

Admin setting:

```text
AI fallback: Enabled / Disabled
```

When disabled and deterministic extraction cannot resolve a readable document:

> This plan requires advanced interpretation, but AI fallback is disabled for this workspace. Upload a clearer document or use Create manually.

Provider/model selection and data-processing terms must be documented before production AI fallback is enabled.

## 9. Review screen

The review screen is a single confirmation stage, not a mandatory row-by-row workflow.

Show:

- source file and page count
- page-quality status
- extracted audit metadata
- auditor/auditee text
- number of inspection items
- number of unique ISO requirements
- detected inspection methods
- inspection-item table in original order
- confidence warnings only where attention is needed
- original-source viewer / signed link

Actions:

- correct extracted metadata
- edit an extracted inspection row
- replace failed page
- abandon import
- create audit

The primary button remains disabled while unresolved blocking errors exist.

## 10. Manual fallback

`Create manually` remains available but becomes secondary.

The current manual scope-clause picker and `buildChecklistForScopes()` behavior are preserved for manual audits. Import-created audits bypass generic scope seeding and instead seed the exact extracted inspection items.

This avoids breaking unusual audits or cases where no formal plan is available.

## 11. File storage and retention

### Temporary imports

Use private storage with an import-specific path such as:

```text
imports/{user_id}/{import_id}/page-001.jpg
imports/{user_id}/{import_id}/page-002.jpg
```

Access is via short-lived signed URLs only.

### After audit creation

The approved source is linked to the resulting audit and retained as an audit source under the audit's normal retention policy.

### Rejected/abandoned imports

Default cleanup target: 7 days after abandonment/rejection, subject to later configuration. Cleanup must never delete source documents already promoted into an operational audit.

## 12. RLS and permissions

RLS remains authoritative.

### Admin

- import and review
- create audit
- manage authorized imports
- enable/disable AI fallback

### Lead Auditor

- import and review
- create audit
- access imports they own or are authorized to manage

### Auditor

- no new global audit-creation privilege introduced by this feature
- can access the source plan only for audits already readable under normal audit RLS

### Viewer

- read-only source access for readable audits
- cannot create/edit imports

### Import security rule

Import ownership does not automatically grant access to an unrelated existing audit. When an import is promoted, ordinary audit membership and RLS become the security boundary.

## 13. Audit trail

Record at minimum:

- uploader
- upload timestamp
- original filename
- document hash
- page count
- page quality outcomes
- OCR/parser version
- AI fallback used: yes/no
- AI provider/model if used
- extraction/confidence summary
- manually corrected fields/items
- resulting audit ID
- promotion timestamp

The system should be able to distinguish:

> manually created audit

from

> audit generated from approved source plan

and retain the source lineage.

## 14. Error states

Explicit error classes:

- `BLURRY_PAGE` -> retake/reupload affected page
- `CROPPED_PAGE` -> retake complete page
- `LOW_CONTRAST` / `GLARE` -> reupload
- `UNSUPPORTED_FILE` -> PDF/JPG/PNG guidance
- `TABLE_NOT_DETECTED` -> AI fallback if enabled, otherwise reupload/manual creation
- `AI_FALLBACK_FAILED` -> no audit created; retry/reupload/manual creation
- `VALIDATION_FAILED` -> show affected fields/items; no silent guess
- `PROMOTION_FAILED` -> no partial audit; keep review-ready import for retry

Analytics and existing audit editing must remain available even if the import subsystem is temporarily unavailable.

## 15. Security and privacy requirements

- uploaded plans are private, never public assets
- signed source links are short-lived
- no service-role credential in the browser
- external AI receives only minimized necessary content
- AI fallback can be disabled by Admin
- raw provider responses are not trusted as operational data
- importer tables use RLS
- file type and size validation applies before processing
- document filenames/user text are escaped in the UI
- uploaded files are not executable by the application
- Supabase security advisors are run after migrations

## 16. Testing and release gates

v0.3.0 cannot be marked released until all applicable gates pass.

### Import behavior

- clear PDF import
- clear phone-photo import
- multi-page import
- single failed-page replacement
- blur rejection
- crop rejection
- low-contrast/glare rejection
- unsupported-file rejection
- exact inspection-item wording preservation
- repeated-clause row preservation
- clause extraction
- inspection-method/tick extraction
- row ordering
- metadata extraction

### AI behavior

- deterministic extraction does not invoke AI when confidence is sufficient
- medium-confidence ambiguous structure invokes AI only when enabled
- AI-disabled path produces explicit fallback guidance
- AI failure creates no operational audit
- malformed AI output fails schema validation

### Review/promotion

- one review screen before creation
- blocking errors disable Create Audit
- corrected values are what get promoted
- promotion creates audit + exact checklist items + source linkage
- transaction rollback prevents partial audit creation
- manual creation still works unchanged

### Security

- import RLS for Admin/Lead/Auditor/Viewer
- unauthorized import/source access denied
- private storage verification
- signed-link expiry behavior
- no secret/provider credential exposed client-side
- source-plan access follows audit RLS after promotion

### Responsive/browser QA

- desktop import/review
- mobile upload/photo flow
- mobile review of long inspection items
- failed-page replacement on mobile
- existing audit/CAPA/analytics regression suite

## 17. Regression fixture strategy

Do not commit the user's actual company audit-plan images as test fixtures unless explicitly authorized.

Create a synthetic test fixture that mirrors the required structure:

- audit header metadata
- numbered inspection rows
- ISO clause/reference column
- inspection-item text column
- Document Review / Inquiry / On-site Inspection columns
- repeated ISO clauses across separate rows
- multi-page continuation

Also create synthetic degraded variants for blur, crop and glare tests.

## 18. Implementation boundaries

Recommended new modules/services should keep responsibilities isolated:

- import UI / review rendering
- document-quality assessment
- OCR/table extraction adapter
- deterministic plan parser
- confidence/validation engine
- optional AI fallback adapter
- import persistence/service layer
- promotion transaction/RPC

Do not add import/OCR/AI responsibilities into the already large `app.mjs` or `views.mjs` beyond routing/orchestration hooks.

## 19. Out of scope for initial v0.3.0

- autonomous audit judgments
- automatically marking conform/nonconform results
- automatic findings or CAPA generation
- semantic rewriting of company inspection questions
- bulk historical-plan migration
- arbitrary template designer
- full document-management/version-control system
- automatic assignment of extracted names to user accounts without confirmation

## 20. Success criteria

v0.3.0 is successful when an authorized user can:

1. choose **New Audit -> Import Audit Plan**,
2. upload a readable plan,
3. have the system automatically detect the audit metadata, ISO requirements, exact inspection items and inspection methods,
4. receive a clear reupload request instead of guessed data when a page is unreadable,
5. review one reconstructed digital plan,
6. press **Create Audit**, and
7. receive an operational Audit Companion audit whose checklist mirrors the approved source plan in the original order, with source-document traceability preserved.

Manual creation remains functional as the fallback path.
